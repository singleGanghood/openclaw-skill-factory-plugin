# Skill 拆解策略 — 诊断标准、拆解模式与决策树

> 本文件定义何时拆、怎么拆、拆成什么样，是 skill-splitter 的核心决策依据。

---

## 一、诊断标准（何时该拆）

任一指标命中即触发拆解评估：

| 信号 | 阈值 | 说明 |
|------|------|------|
| **耗时超标** | 单次运行 > 10 分钟 | 用户感知最明显的信号 |
| **规模超标** | 代码文件 > 20 或总行数 > 5000 | 上下文加载成本高 |
| **功能域过多** | 独立业务能力 ≥ 3 个 | 每个功能域有独立输入/输出 |
| **正文过载** | SKILL.md 正文 > 500 行 | 违反渐进式加载原则 |
| **依赖混杂** | 多个子模块共享代码 + 各自独立入口 | 说明模块边界已可独立 |

### 反例（不该拆）

- 规模小（< 10 分钟、< 5 个文件、单一功能域）→ 拆分增加复杂度
- 模块间强耦合无清晰数据边界 → 硬拆会导致 import 断裂
- 纯文档型 Skill（无代码）→ 结构重组即可，不需拆解

## 二、四种拆解模式

### 模式 A：按功能域拆（横向）

**适用**：各业务能力可独立交付、互不依赖。

```
大 Skill：发票处理（识别+验证+报销+归档）
  ↓
├── invoice-ocr        （识别）
├── invoice-verify     （验证）
├── invoice-reimburse  （报销）
└── invoice-archive    （归档）
```

**关键**：每个子 Skill 有独立入口与产出，数据流单向。

### 模式 B：按流水线阶段拆（纵向）

**适用**：有明显数据依赖链，前序输出是后序输入。

```
大 Skill：客户洞察全链路（候选筛选→信号→标签→洞察→评分→推送）
  ↓
├── orchestrator（薄编排器）
│   ├── candidate-filter    （① 筛选）
│   ├── signal-extractor    （② 信号）
│   ├── tag-engine          （③ 标签）
│   ├── insight-engine      （④ 洞察）
│   ├── recommendation-score（⑤ 评分）
│   └── erp-pusher          （⑥ 推送）
```

**关键**：
- 每阶段间定义**数据契约**（JSON Schema），前序输出 → 后序输入
- 编排器只做串联、超时、失败重试，不含业务逻辑
- 阶段可跳过（如只跑筛选不跑推送）

### 模式 C：按运行类型拆（同步/异步）

**适用**：短同步任务（秒级）与长异步任务（分钟级）混存。

```
大 Skill：混合型（查询 5 秒 + 预计算 30 分钟）
  ↓
├── quick-query     （同步，exec 直接执行）
└── async-precompute（异步，sessions_spawn 隔离执行）
```

**关键**：短任务不被长任务阻塞；长任务独立触发、独立汇报。

### 模式 D：按数据源拆

**适用**：不同外部依赖（ERP 接口、第三方 API）耦合在同一个 Skill。

```
大 Skill：ERP 综合（订单+客户+售后）
  ↓
├── erp-order       （订单接口域）
├── erp-contact     （客户接口域）
└── erp-after-sales （售后接口域）
```

**关键**：按接口域划分，凭证/鉴权共享，业务逻辑分离。

## 三、决策树

```
目标 Skill 运行 > 10 分钟 或 文件 > 20 个 或 功能域 ≥ 3？
├── 否 → 不拆（展示诊断数据，询问用户是否只拆耗时热点）
└── 是 ↓
  子模块间有清晰的数据依赖链（前序输出=后序输入）？
  ├── 是 → 模式 B（按流水线阶段拆）+ 编排器
  └── 否 ↓
    各功能域可独立交付、互不依赖？
    ├── 是 → 模式 A（按功能域拆）
    └── 否 ↓
      存在"秒级查询 + 分钟级预计算"混存？
      ├── 是 → 模式 C（按运行类型拆）
      └── 否 ↓
        不同模块对接不同外部接口域？
        └── 是 → 模式 D（按数据源拆）
```

> 实际大 Skill 常混合多种模式：先按流水线阶段拆，再对长耗时阶段用异步执行。

## 四、拆解后目标形态

```
<original-skill>/                ← 降级为薄编排器
├── SKILL.md                    ← 精简：功能域列表 + 调用顺序 + 数据流
├── orchestrator logic（可选）   ← 若有编排脚本
└── references/                 ← 全局公共文档保留

<sub-skill-1>/  <sub-skill-2>/  ...   ← 每个子 Skill 独立完整
├── SKILL.md                    ← 命令式 description + 数据契约声明
├── scripts/                    ← 自己的模块代码
├── references/                 ← 自己的规则文档
└── assets/
```

**每个子 Skill 必须满足**：
1. 独立可触发（description 有自己的触发词）
2. 独立可运行（输入 → 输出闭环）
3. 耗时 ≤ 10 分钟
4. 通过 skill-assessor 的 `check_structure.sh` 结构检查
5. 数据契约字段与代码实际输入/输出一致
